## A. The ablation study is measuring nothing

### A.1 Runs 23–26 do not contain the components their names claim

`results/*/training_summary.json` records `attention_head` directly from the
variable passed to `_build_backbone`. For the four runs the ablation cites as its
attention and pooling evidence:

| Run | Folder name says | `training_summary.json` says |
|---|---|---|
| 23 | `srm-gem` | `attention_head: "none"` |
| 24 | `srm-cbam` | `attention_head: "none"` |
| 25 | `srm-gem` | `attention_head: "none"` |
| 26 | `srm-cbam` | `attention_head: "none"` |

This is confirmed in the weights themselves, for **both** components. Run 18
(which *was* trained with `--attention_head cbam`) carries CBAM parameters; run 26
does not:

```
$ venv-linux/bin/python -c "..."   # torch.load, list keys
18__...__srm-cbam   348 keys   backbone.features.1.channel_att.mlp.0.weight  ✓
26__...__srm-cbam   345 keys   (no channel_att / spatial_att keys)           ✗
21__...__srm        345 keys
25__...__srm-gem    345 keys
```

Runs 21, 25 and 26 have **identical architectures**.

**Correction (2026-09-08):** an earlier draft said GeM leaves no trace in a state
dict. That is wrong — `attention_heads.py:19` registers `p` as an `nn.Parameter`
unconditionally and only calls `requires_grad_(False)`, so `avgpool.p` **is**
saved. Verified: runs 15 and 17 contain `backbone.avgpool.p`; runs **23 and 25 do
not**. So the absence of GeM in 23/25 is provable from the weights alone, not
merely from the recorded config. The claim is stronger than originally stated.

`results/ablation_study.md` rows *"Attention (CBAM) | 26"* and *"Pooling (GeM) |
25"* therefore describe models containing neither. Those two rows, and the
`−0.07` / `+0.12` deltas derived from them, have to come out.

### A.2 Runs 25 and 26 are the same experiment run twice

They differ in no recorded field. That makes them an accidental — and very
useful — replicate. On the 23,341-image test set:

```
run25 acc 0.8973   run26 acc 0.8958
they disagree on 991 of 23,341 samples (4.2%)
McNemar b=513 c=478  p = 0.28
```

**0.15 percentage points is the run-to-run noise floor of this setup.** Every
claimed effect in the ablation is smaller than that.

### A.3 The SRM result does not survive a significance test

Paired McNemar on the saved `y_true.npy` / `y_pred.npy`:

| Comparison | acc A | acc B | Δ | McNemar p |
|---|---|---|---|---|
| 19 baseline → 21 +SRM | 0.8972 | 0.8967 | **−0.0006** | 0.725 |
| 19 baseline → 22 +SRM+FFT | 0.8972 | 0.8946 | −0.0026 | 0.081 |

The `+0.14 pp` SRM gain in the ablation comes from `best_val_acc`, which is the
*maximum over epochs* of a noisy per-epoch quantity — a max-over-25-draws is a
biased estimator and will favour whichever run happened to spike. **On the test
set the sign flips and SRM is marginally worse, at p = 0.73.**

The honest statement is: *SRM, FFT, CBAM and GeM produce no measurable change on
this dataset.* That is a legitimate and publishable negative result, and it is
more defensible than the current `+0.14 pp` claim, which a reviewer will take
apart in about ten minutes.

### A.4 Two saved prediction sets are garbage and one is quoted as if it isn't

```
run 20 (FFT)   best_val_acc 0.8837   →  saved y_pred accuracy 0.3491  (chance)
run 18 (CBAM)  best_val_acc 0.8356   →  saved y_pred accuracy 0.7094
```

Cause, run 20 — `scripts/evaluation/evaluate.py:402-403` detects the preprocessing
wrapper by searching key *names*:

```python
has_srm = any("srm" in k.lower() for k in raw_sd)
has_fft = any("fft" in k.lower() or "FFT" in k.lower() for k in raw_sd)
```

`SRMLayer` registers a `kernels` buffer so `srm.kernels` appears in the state
dict and SRM is detectable. **`FFTLayer` has no parameters and no buffers**, so an
FFT-only checkpoint contains zero keys matching either pattern. Verified: run 20's
checkpoint has no key containing `srm` or `fft`, and its stem is `(96, 4, 4, 4)`.
The model is rebuilt as a plain 3-channel ConvNeXt, the stem is then coerced to
4 channels by the best-effort adapter, and no FFT layer is ever attached.

Cause, run 18 — `attention_head` is a *command-line argument* to `evaluate.py`,
not something read from the checkpoint. Evaluate a CBAM checkpoint without
`--attention_head cbam` and the CBAM tensors land in `unexpected_keys`, where
`load_state_dict(raw_sd, strict=False)` at `evaluate.py:617` silently discards
them.

`results/20/confusion_matrix.png` and the `y_*.npy` files for both runs should be
deleted or regenerated. Nothing downstream should read them.

## B. `evaluate.py` cannot currently evaluate 21 of the 25 runs

```
$ venv-linux/bin/python -c "from evaluation.evaluate import load_model; load_model('models/21__.../best_model.pth','cpu')"
TypeError: _build_srm_net() got an unexpected keyword argument 'num_classes'
```

`load_model` passes `num_classes=target_num_classes` (`evaluate.py:461`);
`_build_srm_net` (`evaluate.py:186`) has no such parameter. This fires for every
checkpoint where `has_srm or has_fft` — which is every SRM run, including run 21,
the best model in the repo. The in-process cascade path at `evaluate.py:726` goes
through the same `load_model`, so `CascadeClassifier` is unreachable for the real
models too.

One-line fix, but it means **no number in the repo can be reproduced right now**.

### B.1 `strict=False` plus bare `except` is how A.4 happened

`evaluate.py:610-617`:

```python
    except Exception:
        # best-effort adaptation — if anything goes wrong, continue to loading
        pass

    model.load_state_dict(raw_sd, strict=False)
```

Between them, an architecture that does not match the checkpoint produces a model
that is partly or wholly untrained, and then reports a number for it. Runs 18 and
20 are the evidence, and instrumenting `load_state_dict` shows both are worse than
originally stated:

- **Run 20 loads ZERO weights.** `missing=344, unexpected=344` — the built model
  is a bare ConvNeXt (`features.*`) while the checkpoint is `backbone.*`, a total
  prefix mismatch. Since `weights=None`, the evaluated model is **100%
  randomly initialised**, not "partly pretrained" as an earlier draft said. Hence
  the chance-level 0.3491.
- **Run 18 is evaluated as a truncated ConvNeXt-Tiny.** `evaluate.py:415` detects
  Small by the substring `features.5.20`, but `_build_backbone` re-nests
  `m.features = Sequential(m.features, cbam)`, so a CBAM checkpoint's keys read
  `backbone.features.0.5.20.*` and the pattern misses. Tiny and Small have
  identical channel widths and differ only in depth ([3,3,9,3] vs [3,3,27,3]), so
  the wrong model loads with **no size mismatch at all**: `missing=0,
  unexpected=162` — exactly the 18 surplus stage-3 blocks x 9 tensors. This
  happens **even when `--attention_head cbam` is supplied**, so it, not the
  missing flag, is the real cause of run 18's 0.7094.

Change to `strict=True` and let it crash. If you need the tolerant path, at
minimum assert `len(missing) == 0 and len(unexpected) == 0` and print both.

### B.2 Architecture should be read from the config, not guessed from key names

`load_model` reconstructs the model from heuristics — `"features." in k`,
`"features.5.20" in k`, `v.shape[-1] == 2048`, `"srm" in k.lower()`. Every one of
these is a guess that fails silently. `training_summary.json` sits next to the
checkpoint and records `backbone`, `use_srm`, `use_fft`, `attention_head`,
`dropout_p`. Save it *into* the checkpoint:

```python
torch.save({"state_dict": model.state_dict(), "config": summary["config"]}, path)
```

and have one `build_model_from_config()` shared by `train_full.py`,
`evaluate.py` and `frontend/inference.py`. There are currently **three separate
reimplementations** of the same model construction, and they disagree — which is
section C.

## C. The frontend cannot load the best model

```
$ venv-linux/bin/python -c "from frontend import inference; inference.load_model('models/21__convnext-small__light__0.4__cosine__focal__srm/best_model.pth', device='cpu')"
TypeError: 'Conv2d' object is not subscriptable
```

`frontend/inference.py:120-122`:

```python
stem = model.features[0][0]   # this is already the Conv2d
stem[0] = adapt_conv1_for_srm(stem[0])   # subscripting a Conv2d
```

For torchvision 0.25, `convnext_small.features[0]` is a `Conv2dNormActivation`
and `features[0][0]` is the `Conv2d` itself. Confirmed on the installed version.

Consequences:
- **No ConvNeXt + SRM checkpoint can be opened in the Streamlit app.** That is
  runs 06, 08–14, 17, 18, 21, 22, 25, 26 — including the headline model.
- `frontend/config.py` defaults to run 19, the RGB-only model, which is the one
  ConvNeXt checkpoint that happens to avoid this path. The app works by accident.
- FFT-only and SRM+FFT checkpoints are undetectable here for the same reason as
  A.4 (`has_srm = any(k.startswith("backbone."))` is true for FFT-only models, so
  it builds an SRM wrapper and a 6-channel stem for a 4-channel checkpoint).
- `attention_head` is never handled at all — `GeM` and `CBAMBlock` are imported
  at the top of the file and never used.

`train_full.py` gets this right at line 370 by recursively searching for the first
`Conv2d`. `evaluate.py` gets it right with a `try/except` fallback. Only the
frontend hardcodes the wrong shape. This is the argument for one shared builder.

## D. The dataset pipeline dedups per-source, so cross-source leakage is invisible

This is a sharper version of BACKLOG item 1, and I think it matters more.

There is **one config per source** (`dataset_builder/config/ai_edited_defacto_config.yaml`,
`real_coco_config.yaml`, …), each with its own `source_dirs`, its own
`split_ratios: 0.7/0.15/0.15`, and its own pipeline invocation. So
`build_clusters` → `assign_clusters_to_splits` → `validate_no_leakage`
(`modules/splitter.py`) all run **within a single corpus**. The pHash clustering
never compares an image in one source against an image in another.

The only cross-source step is `tools/merge_exports.py`, which deduplicates on
`(md5_hash, sha256)` — bit-identical files only.

Why this is not academic:

- **DEFACTO and CASIA are built on top of COCO images.** A DEFACTO inpainted image
  and its COCO original differ only in the inpainted region. Their MD5s differ, so
  the merge keeps both; their pHashes are close, but they were never compared,
  because they went through two separate pipeline runs.
- The COCO original can therefore sit in `train/real` while its DEFACTO derivative
  sits in `test/ai_edited`, or vice versa. That is direct train/test contamination
  across the exact class boundary — Real ↔ AI-Edited — that the whole project is
  about, and where 69% of errors fall.
- The same applies to FaceForensics++ and ForgeryNet, whose originals are also
  drawn from public video corpora.

The README's claim — *"Cluster-based splitting prevents similar images from
leaking across train/test"* — is true within a source and false across sources.
The same claim appears in `docs/EXTERNAL_BENCHMARK.md` as *"leakage-resistant
cluster splitting"*.

**Measure it before anything else.** Compute pHashes over the merged
`export_index` and count cross-source, cross-split pairs at Hamming ≤ 8. This is
one pass over the manifest, no retraining, and it either clears the dataset or
tells you the 89% is partly memorisation. Do it before the leave-one-source-out
work in BACKLOG 1.1, because if there is contamination, LOSO numbers computed on
the current export are also affected.

### D.1 The clustering threshold is close to a no-op anyway

`phash_bucket_chars: 12`, `phash_cluster_threshold: 8`, on 16-hex-char (64-bit)
pHashes. Two images are only ever *compared* if their first 12 hex characters —
48 of 64 bits — are **exactly equal**, and are then clustered if the full Hamming
distance is ≤ 8. Those two conditions barely overlap: a pair 8 bits apart is very
unlikely to have 48 identical leading bits. In practice this is close to
exact-prefix matching and misses most genuine near-duplicates.

Use a proper multi-index scheme: split the 64 bits into 4 bands of 16, bucket on
each band separately, and compare within any shared band. That catches everything
within Hamming ≤ 3 exactly and most of ≤ 8, at similar cost.

## E. The focal loss is not doing what the docstring says

`scripts/training/losses.py:96-107` computes the modulating factor from the
*weighted, label-smoothed* cross-entropy:

```python
ce = F.cross_entropy(logits, targets, weight=self.weight,
                     reduction="none", label_smoothing=self.label_smoothing)
pt = torch.exp(-ce)
focal_loss = (1.0 - pt) ** self.gamma * ce
```

`pt = exp(-ce)` only equals the model's probability for the correct class when
`ce` is the plain unweighted, unsmoothed cross-entropy. With the project defaults
(`gamma=3.0`, `label_smoothing=0.1`, `class_weights=[1.5, 1.0, 1.5]`) it is
neither. Measured, for a sample the model gets right with probability `p`:

| p(correct) | class | true `(1-p)^γ` | implemented `(1-pt)^γ` | ratio |
|---|---|---|---|---|
| 0.99 | Real (w=1.5) | 0.000001 | 0.04900 | 49,000× |
| 0.99 | AI-Gen (w=1.0) | 0.000001 | 0.07240 | 72,000× |
| 0.90 | Real | 0.00100 | 0.03521 | 35× |
| 0.70 | Real | 0.02700 | 0.11186 | 4.1× |
| 0.50 | Real | 0.12500 | 0.29066 | 2.3× |

Two separate problems:

1. **Label smoothing puts a floor under `ce`**, so `pt` can never approach 1 and
   the focal term never approaches 0. A 99%-confident correct prediction is
   down-weighted by 0.049, not by 10⁻⁶. The mechanism the docstring describes —
   *"a 95%-confident correct prediction contributes only 0.0025× its normal
   loss — effectively ignored"* — does not happen. What you have been running is
   much closer to weighted CE with a mild reweighting than to focal loss.
2. **The class weight leaks into the modulating factor**, making it class-
   dependent. Note the inversion in the table: at p=0.99 the Real class (weight
   1.5) gets a *smaller* modulator (0.049) than AI-Generated (weight 1.0, 0.072).
   The intended and actual emphasis point in opposite directions in the regime
   where most of the data sits.

Fix:

```python
logp  = F.log_softmax(logits, dim=1)
pt    = logp.gather(1, targets[:, None]).squeeze(1).exp()   # true probability
ce    = F.cross_entropy(logits, targets, weight=self.weight,
                        reduction="none", label_smoothing=self.label_smoothing)
loss  = (1.0 - pt) ** self.gamma * ce
```

This is worth fixing *and worth writing up*: "our focal implementation had a
label-smoothing interaction that neutralised the focusing term, and correcting it
changed results by X" is a real methodology finding. It also gives you a genuine
ablation axis to replace the null ones in section A.

## F. FFT features are batch-dependent

`scripts/preprocessing/fft.py:22-24`:

```python
magnitude = (magnitude - magnitude.min()) / (magnitude.max() - magnitude.min() + 1e-8)
```

`.min()` and `.max()` with no `dim` reduce over **every** dimension including the
batch. Each image's FFT channel is normalised by statistics of whatever other
images happened to share its batch. Consequences:

- The same image gets different features at batch size 64 and batch size 1, so
  training and single-image inference disagree.
- Information flows between samples within a batch, which is a (mild) form of
  leakage during training.
- Results are not reproducible across batch sizes.

Fix: `amin(dim=(1,2,3), keepdim=True)` / `amax(...)`, i.e. per-sample.

This alone probably explains why FFT was the only component to visibly *hurt*
(run 20, `best_val_acc` 0.8837 vs 0.8940 baseline) — it is the one component with
an actual bug in its feature computation, as distinct from being merely useless.

### F.1 SRM operates on normalised pixels

`preprocessing.py` applies `A.Normalize()` (ImageNet mean/std) *before*
`ToTensorV2`, so `SRMLayer` receives standardised values, not [0,1] pixels. The
`clamp_range=2.0` in `srm.py` was chosen for the conventional SRM setting and now
clamps at ±2 standard deviations of a residual whose scale is ~4.4× larger than
intended (1/0.226). Not fatal — the network can rescale — but it means the clamp
is doing much less than the comment claims, and the "SRM does nothing" result in
A.3 should be re-tested with the residual computed on raw pixels before you
conclude SRM is genuinely useless.

## G. Smaller correctness issues

1. **`use_fft` is not read from YAML.** `train_full.py:170-200` reads `use_srm`
   from the config dict but never `use_fft`. A config file setting `use_fft: true`
   trains without FFT and reports `use_fft: false`, with no warning. (Run 20 was
   launched via CLI so it escaped, but the trap is live.)

2. **`train()` reads a module-level `args` global.** `getattr(args, "dry_run",
   False)` appears eight times inside `train()`, and `args.max_steps` /
   `args.dry_run` are accessed unguarded inside the profiler branch
   (lines 471-476). Importing `train_full` and calling `train()` programmatically
   — which `weight_sweep.py`-style scripts want to do — raises `NameError`. Pass
   `dry_run` and `max_steps` as parameters.

3. **Checkpoints carry the `torch.compile` prefix.** `model = torch.compile(model)`
   at line 393 runs unconditionally (`hasattr(torch, "compile")` is always true),
   so every saved `state_dict` has `_orig_mod.` on every key. Both loaders strip
   it, so this works — but it is a landmine for any third loader, and the fix is
   one line: save `model._orig_mod.state_dict()` when compiled.

4. **`CosineAnnealingWarmRestarts(T_0=20, T_mult=2)` with `early_stop_patience=7`.**
   Runs stop at 11–30 epochs. The first restart is at epoch 20, so most runs get a
   sudden LR jump back to `1e-4` in their final third, then early-stop shortly
   after. Runs 18 and 20 stopped at 11 epochs — before completing even half a
   cycle. Given `epochs=50` and a patience of 7, either use `CosineAnnealingLR`
   over the real budget or set `T_0` to something the runs actually reach. This is
   a plausible contributor to the run-to-run churn in A.2.

5. **`CascadeClassifier` buffers the entire test set in RAM.**
   `cascade_classifier.py:75` accumulates `images_buffer` as float32 CPU tensors —
   23,341 × 3 × 224 × 224 × 4 B ≈ **14 GB** — then `cand_imgs = all_images[candidates].to(device)`
   moves every candidate to the GPU at once. It will OOM on the real test set. It
   also duplicates the logic in the four-script `run_cascade_pipeline.py` path with
   no shared code and no test that the two agree.

6. **`scripts/dataloader/dataset_loader.py` is dead *and* broken.** BACKLOG item 2
   is right that it should go. It is worse than the backlog says: `torch` is never
   imported, so `torch.utils.data.Subset` at line 76 raises `NameError` — the
   function has never run. Delete the file.

   Note for the backlog: BACKLOG item 1's *diagnosis* is correct but the file it
   cites is this dead one. Training goes through `get_data_loaders` in
   `train_full.py`, which uses the pre-built `dataset_builder/val` directory. The
   source↔class confound is real regardless of which splitter you use — it is a
   property of the dataset, not the split — so the conclusion stands. Worth fixing
   the citation so a reader doesn't check the file and dismiss the whole item.

7. **`DeepfakeDataset.__getitem__` has no error handling.** `cv2.imread` returns
   `None` for an unreadable file and `cv2.cvtColor(None, ...)` then crashes with
   an unhelpful OpenCV error and no filename. One `if image is None: raise
   RuntimeError(img_path)`.

8. **No tests, no CI, unpinned requirements.** `requirements.txt` has no version
   constraints at all — and section C is exactly a torchvision-version-dependent
   break. Pin the versions you actually ran.

# Addendum — why it fails on real images but works on dataset images

Reported symptom: the model classifies dataset images correctly and fails on
arbitrary images. There are **two independent causes**, and they need separating
because one is a five-line fix and the other is a retrain.

## Cause 1 — training and inference resize images differently (deployment bug)

Training (`scripts/preprocessing/preprocessing.py` → `A.Resize(224,224)`) goes
through **OpenCV `INTER_LINEAR`, which does not antialias when downsampling**.
Inference (`frontend/inference.py:145` → `transforms.Resize`) goes through
**PIL bilinear, which does antialias**. Same image, same content, different
high-frequency content:

```
60 FLUX images, native 1024x1024, resized to 224 two ways:
  TRAIN path (cv2 INTER_LINEAR, no antialias)  HF energy 0.5199 +- 0.0548
  INFER path (PIL bilinear, antialiased)       HF energy 0.3377 +- 0.0461
  -> inference strips 35% of the high-frequency energy
  -> the gap is 3.3 training standard deviations
```

("HF energy" = fraction of FFT magnitude outside the central quarter-radius.)

Every image entering the Streamlit app therefore lands 3.3σ outside the training
distribution, in exactly the frequency band a manipulation detector keys on. This
happens to dataset images and user images alike.

**This also invalidates the comparison that produced the symptom.** The 89%
numbers were measured through `DeepfakeDataset`, which loads with `cv2.imread`
and applies the albumentations transform. The failures were observed through the
Streamlit app, which loads with PIL and applies a torchvision transform. "Works
on the dataset, fails on my images" is partly "works through the cv2 path, fails
through the PIL path" — the two observations were never made through the same
pipeline.

**Fix — make inference use the training transform verbatim:**

```python
# frontend/inference.py
import cv2
from preprocessing.preprocessing import val_transform

def preprocess_image(pil_image):
    img = cv2.cvtColor(np.array(pil_image.convert("RGB")), cv2.COLOR_RGB2BGR)
    img = cv2.cvtColor(img, cv2.COLOR_BGR2RGB)          # match the dataset's exact path
    return val_transform(image=img)["image"].unsqueeze(0)
```

Then re-test on the same images. Do this **before** any retraining — it costs
nothing and it tells you how much of the failure is a bug rather than a
generalisation limit. Same fix applies to `frontend/gradcam.py` and
`demo_gradcam.py` if they preprocess independently.

Longer term the transform should live in one module that training, evaluation and
the app all import, rather than being written out three times.

## Cause 2 — source resolution is a corpus fingerprint, and it survives the resize

The exporter uses `shutil.copy2` (`dataset_builder/modules/exporter.py:25`), a
byte-for-byte copy. So every image keeps its **source corpus's native encoding and
resolution**, untouched. Measured on what is still on disk:

```
data_sources/ai_generated/FLUX             1500/1500 images are exactly 1024x1024
data_sources/ai_generated/Midjourney_TopUp resolutions 520x520, 1024x1024, 260x520, 864x1728, ...
```

FLUX is a single resolution, 100% of the time.

`A.Resize(224,224)` does not remove this. The *downsample ratio* leaves a
signature, because non-antialiased downsampling aliases in proportion to how much
it shrinks. Same 40 images, artificially given different native resolutions, all
through the training resize:

```
  native 1024px -> 224 : HF energy 0.5255 +- 0.0445
  native  512px -> 224 : HF energy 0.4611 +- 0.0469
  native  260px -> 224 : HF energy 0.3473 +- 0.0408
```

Identical content. The native resolution alone separates them by ~4σ. Since each
corpus has a characteristic resolution distribution, and each corpus maps to
exactly one class (BACKLOG item 1), **"what was this image's original resolution"
is a near-free, near-perfect class label** — and it lives in the same frequency
band as the SRM residuals and the FFT channel.

An arbitrary photograph has an arbitrary resolution, so it produces a downsample
signature matching no corpus, and gets assigned to whichever one it happens to
resemble. That is the observed behaviour.

Aspect ratio does the same job independently: `A.Resize(224,224)` squashes a
260x520 image to square and leaves a 1024x1024 one unchanged, so "was this
stretched, and by how much" is another free corpus cue.

## The augmentation results already told you this

Grouping every run by augmentation strength:

| Augmentation | Runs | Best val acc |
|---|---|---|
| `light` (resize + flip only) | 09, 11, 12, 13, 19, 21, 22, 25, 26 | 0.889 – 0.895 |
| `standard` (+ rotate, brightness, JPEG 30-100) | 10 | 0.866 |
| `strong` (+ wider JPEG, noise, blur) | 08, 15, 16, 17, 18 | 0.828 – 0.843 |

Perfectly monotone, and inverted: **the more the augmentation destroys, the worse
validation gets.** That is the signature of a shortcut. Augmentation was removing
a cue that validation rewards, because validation shares the training corpora. The
5-point "loss" from strong augmentation is not the augmentation failing — it is
the augmentation working, and the validation set punishing it.

The model selection procedure therefore selected *for* the shortcut. Run 19/21
(`light`) is the most corpus-dependent model in the repo, and run 19 is what
`frontend/config.py` ships. The runs most likely to work on your own photographs
are the `strong` ones that scored worst.

## What to do, in order

1. **Fix the resize mismatch and re-test on the same failing images.** Five lines,
   no retraining. Establishes the baseline before you conclude anything.
2. **Test run 17 or 18 (`strong` augmentation) on those same images**, through the
   corrected pipeline. If they beat run 19 on your photographs while scoring 5
   points worse on validation, the shortcut hypothesis is confirmed end-to-end and
   you have the single best figure in the whole write-up.
3. **Add resize-ratio and aspect randomisation to the augmentation.** The current
   `strong` mode varies JPEG quality, noise and blur, but every image still takes
   exactly one deterministic path to 224x224. Add: random downscale to a random
   intermediate size then back up, `RandomResizedCrop` with a wide scale range,
   and randomised interpolation (`cv2.INTER_AREA` / `INTER_LINEAR` / `INTER_CUBIC`).
   This attacks the specific cue measured above.
4. **Normalise the corpus at build time.** Re-encode every exported image to a
   common resolution and JPEG quality with a single encoder. That removes
   resolution, quantisation table and encoder fingerprint in one step. It costs one
   re-export and it makes every subsequent number mean more. Note this must happen
   *after* the cross-source pHash audit in section D, not before, or you destroy
   the evidence.
5. **Only then** re-run the ablation. Under a corpus-normalised dataset with
   resize augmentation, SRM and FFT are finally being asked the question they were
   introduced to answer, and the section A null result may well change.

A caution on expectations: after fixing (1)-(4) the validation number **will
fall**, probably a lot. That fall is the shortcut being removed, not the model
getting worse, and the resulting figure is the first one that actually predicts
behaviour on your own photographs. Say so explicitly in the write-up rather than
presenting the drop as a regression.

Findings beyond those above. All verified by execution.

## I. Every Grad-CAM figure in the project is colour-inverted

`frontend/gradcam.py:222` uses `cv2.applyColorMap`, which returns **BGR**;
`:225` reads the photo as **RGB**; `:228` blends them and `:231` interprets the
result as RGB. Measured on a uniform grey image with `alpha=1.0`, jet:

```
OpenCV path (the default)  importance=1.0 -> [  0   0 128] BLUE
                           importance=0.0 -> [128   0   0] RED
matplotlib path            importance=1.0 -> [127   0   0] RED    (correct)
                           importance=0.0 -> [  0   0 127] BLUE   (correct)
CV2_AVAILABLE = True  ->  the inverted path is the one that runs
```

**The most important regions render blue and the least important render red**, in
the Streamlit app, in `demo_gradcam.py`, and in every saved figure.
`frontend/app.py:203` tells the user in words that "red/hot areas are the pixels
that pushed the model toward that prediction" — the exact opposite of what is on
screen. Because jet is roughly R<->B symmetric in the mid-range, an inverted map
still looks like a plausible Grad-CAM, which is why it survived.

`create_gradcam_comparison` contains the proof inside a single figure: its middle
"raw heatmap" panel uses matplotlib and is correct; its right "overlay" panel uses
the OpenCV default and is inverted. Same input, `[127,0,0]` vs `[0,0,128]`.

Fix: one `cv2.cvtColor(heatmap_colored, cv2.COLOR_BGR2RGB)` at `:222`.
**Every published Grad-CAM figure must be regenerated afterwards.**

### I.1 The target layer is also wrong

`gradcam.py:77-79` selects the **last `nn.Conv2d` in `reversed(model.modules())`**.

- ConvNeXt: picks `features.7.2.block.0`, the 7x7 *depthwise* conv at the entrance
  of the last block — pre-LayerNorm, pre-MLP, pre-layer-scale, pre-residual. Against
  the canonical CAM hooked on `backbone.features`, Pearson **r = 0.598**. The
  figures are not the standard quantity.
- ResNet-50: picks `layer4.2.conv3`, a 1x1 conv, pre-BN, pre-residual, pre-ReLU.
- **Any CBAM model: picks CBAM's spatial-attention conv, which has ONE output
  channel.** `cam = sum(w * activations, dim=1)` over a single channel is then
  `+/-` the spatial attention logit map times a scalar — **class-independent, and
  carrying no Grad-CAM information at all.** Affects runs 16 and 18.

Fix: an explicit per-architecture map (`layer4` for ResNet, `features` for
ConvNeXt), never a 1-channel conv. ~20 lines.

### I.2 A degenerate CAM renders as solid red

`gradcam.py:156-158` returns all zeros when the CAM is uniform. Through the
inverted path, zeros -> jet minimum -> **solid red**, i.e. the failure case
displays as maximum attention everywhere. `app.py:250-261` generates exactly this
in the three-class comparison panel.

## II. SRM is switched off at initialisation — a mechanistic explanation for A.3

`srm.py:155`: `fill = rgb_weights[:, :1, ...].repeat(1, extra, 1, 1) * 0.1`
tiles the **R-channel** weights across all three residual channels. Measured on
`resnet18.conv1`:

```
RGB channel norms       [7.2079, 8.6385, 5.6271]
residual channel norms  [0.7208, 0.7208, 0.7208]
residual ch3 == ch4 == ch5 : True
```

Two defects:

1. **The three residual channels get bit-identical weights.** At init the conv
   computes `0.1 * W_R * (r_laplacian + r_horizontal + r_vertical)`. The module
   docstring's "covering different frequency orientations" is annihilated by its
   own initialisation. Gradients break the tie, but from a perfectly degenerate
   start.
2. **The residual branch contributes ~1/1250 of the pre-activation variance.**
   Combining weight norms with measured activation scales (RGB std 1.329,
   clamped-residual std 0.377): RGB 279.61 vs residuals 0.2215, ratio **0.0008**.
   To become material the residual weights must grow ~35x in norm; at `lr=1e-4`
   over the 11-30 epochs these runs lasted, that does not happen.

This is a **mechanistic, non-statistical explanation for section A.3's "SRM does
nothing"**, independent of the McNemar argument and much harder to dismiss. A
sane per-channel init scaled to the measured `residual std / RGB std = 0.28`
would be a genuinely different experiment from the one that was run. ~8 lines,
and it is the only change with a real chance of turning the null ablation into a
result.

Separately, the `clamp_range=2.0` argument is **inert**: 0.498% of values are
clipped as run, and 0.000000% in the intended `[0,1]` regime. Section F.1's
concern about the clamp can be closed — it changes nothing either way.

## III. FFT batch dependence, quantified

Same fixed image, per-sample vs batched normalisation:

```
batch size    min      max      mean
    1       0.0000   1.0000   0.4065
    8       0.1730   0.9585   0.5011
   32       0.2295   0.9660   0.5344
   64       0.2124   0.9585   0.5421
```

Training ran at `batch_size=64`; frontend inference is `batch_size=1`. **The 4th
input channel's mean shifts by 0.136 — 14% of its full range — between training
and deployment**, independent of every loading bug.

Also: mean pairwise Pearson r between *different* images' FFT channels is
**0.349** (RGB reference: 0.215), and the batch-mean FFT image explains **28.0%**
of the variance. It is a frequency-domain map being fed to a spatially-local
convolution, so the conv's locality prior is meaningless on it. Fixing the
normalisation gives a correct implementation of a questionable idea; expect to
report run 20 as a negative result either way.
